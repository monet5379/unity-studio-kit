# 글쓰기 가이드 (Unity Kit)

이 Kit의 `docs/`와 프로젝트 `AGENTS.md`·README를 쓸 때 따른다.  
토스 [테크니컬 라이팅](https://technical-writing.dev/overview.html)([GitHub](https://github.com/toss/technical-writing))의 **유형 · 정보 구조 · 문장**만 Unity 작업에 맞게 축약했다.  
에이전트·AI 초안의 문체는 [im-not-ai](https://github.com/epoko77-ai/im-not-ai)의 의미 불변·서법 보존·번역투 일부만 한다체 문서에 맞게 줄였다. 분류 체계 전문과 윤문 파이프라인은 이 Kit에 두지 않는다.  
사이트 notes·Jekyll 전용 규칙은 여기에 두지 않는다.

## 적용 범위

- 이 Kit의 `docs/` · `templates/` 사람용 본문
- `profile: game` 타이틀의 `docs/**` · `Docs/**` · `AGENTS.md`

## 독자 · 톤


|     |                                                         |
| --- | ------------------------------------------------------- |
| 독자  | 몇 달 뒤의 본인, 새 Unity 프로젝트를 붙이는 본인. (에이전트는 `.mdc` 요약을 본다.) |
| 톤   | **한다체**로 통일. 1인칭 허용. (토스 가이드와 같은 말투 축.)                 |
| 목표  | 규칙을 외우게 하지 않고, **다음에 무엇을 하면 되는지** 바로 알게 한다.             |


Kit `docs/` · README · `templates/` 사람용 본문은 **한다체**로 맞춘다. **신규·수정 구간**(한 문단·한 bullet만 고쳐도 해당 구간 전체)도 **한다체**로 쓴다. 주변에 합니다·해요체가 남아 있어도, 손댄 구간은 한다체로 맞춘다. (프로젝트 `/ponytail` 스킬처럼 긴 에이전트 지침은 요약 톤을 유지할 수 있다.)

**톤 예외:** `notes/` · `interview/` (및 타이틀 `AGENTS.md`에 명시한 경로)는 구어체·평서체를 허용한다. Architecture · Optimization · GDD `locked` 본편은 한다체를 유지한다. 톤 예외 경로가 아니면 신규·수정 구간에도 예외를 적용하지 않는다.

## 정본 사다리 (game 권장)

충돌할 때는 아래 순서로 맞추한다.

```text
코드 ≥ Architecture ≥ 설계 정본
```

설계 정본은 GDD `locked`(또는 Decision), 또는 Technical Design이다. 타이틀 `AGENTS.md`가 경로를 정한다.

- **코드**가 현재 동작의 최종 정본이다.
- **Architecture**는 구조·경계·계약의 문서 정본이다. 코드와 어긋나면 Architecture를 고치거나 코드 변경을 되돌리한다.
- **설계 정본**은 구현 근거로만 쓰고, Architecture·코드보다 우선하지 않는다. GDD는 `locked`(또는 Decision)만 해당한다.

## docs와 rules


|                    | 역할                                       |
| ------------------ | ---------------------------------------- |
| `docs/**`          | **사람용 정본** — lead · 왜 · 예시 · 표           |
| `.cursor/rules/**` | **에이전트용 요약** — Must / Must not + docs 링크 |


내용이 바뀌면 **docs를 먼저** 고치고, rules는 짧은 요약만 맞추한다. 규칙 전문을 `.mdc`에 장문으로 쓰지 않는다.

## 정보 구조

1. **가치를 먼저 (lead)** — 문서 첫 2~4문장에 “이 페이지가 무엇을 결정·가능하게 하는가”를 쓴다.
2. **개요를 빼지 않기** — 필요하면 lead 다음에 전제·독자·관련 링크를 짧게.
3. **한 페이지 한 주제** — Overview와 AssetsLayout을 한 파일에 합치지 않는다.
4. **예측 가능한 목차** — 아래 유형별 골격을 기본으로, 필요 섹션만 두한다.
5. **제목** — 무엇/왜가 보이게. 부제(`—`)는 쓰지 않는다.

표·불릿은 **스캔용**으로 유지한다. 표만으로 끝내지 말고, lead나 한두 문장으로 맥락을 주한다.

## 문장

- **주어를 분명하게** — 독자·작성자·에이전트. 시스템 주어는 동작·경계 설명에만.
- **필요한 정보만** — “~할 수 있다” 남발 대신 허용/금지를 단정한다.
- **용어 통일** — `profile`, `common` / `personal` / `game`, `Architecture`, Plan.
- **의도적 범위 제한**은 유지한다 (`기각`, `이 Kit에 두지 않음`).
- 경로·asmdef·명령은 꾸미지 않고 **참조 톤**으로 적는다.
- **문체:** 본문은 **한다체**(`~한다`, `~이다`, `~하지 않는다`). **신규·수정 구간** 포함. **합니다체·해요체**는 쓰지 않는다 (톤 예외 경로 제외).

## 에이전트·AI 초안

에이전트가 쓴 초안을 Kit 문서로 다듬을 때 이 절을 따른다. 유형·lead·골격·한다체는 위 절이 우선한다. `notes/`·`interview/` 초안을 외부 윤문으로 다듬을 수 있다. 본편에 넣기 전에 한다체·lead·경로를 이 가이드로 다시 맞춘다.

### 원칙

- **의미 불변.** 경로·asmdef·API·수치·고유명사·`Must` / `Must not`·금지 목록은 문장을 다듬을 때 바꾸지 않는다.
- **서법·강도 보존.** 당위(`~해야 한다`)를 사실(`~한다`)로 내리지 않는다. 가능성·유보를 단정으로 올리지 않는다. 허용·금지·선택은 서로 바꾸지 않는다.
- **국소 수정.** AI 티가 있는 문장·bullet만 고친다. lead와 골격이 맞으면 페이지를 통째로 다시 쓰지 않는다.
- **과윤문 가드.** 한 번에 고친 분량이 해당 페이지의 약 30%를 넘으면, 문체 문제인지 골격·정본 문제인지 나눈다. 절반을 넘는 전면 윤문은 하지 않는다.
- **빼기.** 고치는 문장에 원문에 없던 AI 상투구를 넣지 않는다. 한다체를 더 격식 있게 올리지 않는다 (`했`을 `하였`으로 바꾸지 않는다).
- **본편 톤.** Architecture·Optimization·GDD `locked`·프로세스 본편은 한다체를 유지한다. `notes/`·`interview/`는 구어를 그대로 둘 수 있다.

### 문장에서 줄일 표현

보이는 표현을 아래 방향으로 고친다. 코드·타입·경로·Unity 용어·수치·인용은 그대로 둔다.

| 보이는 표현 | 고치는 방향 |
| --- | --- |
| ~에 대해(서) | 주제를 주어·목적어로 바로 쓴다 |
| ~에 있어(서) | `~에서`로 줄이거나 해당 구를 뺀다 |
| ~가지고 있다 | `~가 있다` |
| ~되어진다, ~에 의해 | 능동 또는 단순 피동. 규범 서술(에이전트는 ~한다)은 유지한다 |
| ~할 수 있다 반복 | 허용·금지·선택 중 하나로 단정한다. 서법 강도는 유지한다 |
| 문두 `그리고`, `결론적으로`, `따라서`, `이를 통해`가 한 페이지에 여럿 | 문장을 잇거나 접속을 뺀다 |
| ~에서의, ~에로의, ~으로의 | 조사를 한 겹으로 줄인다 |
| 설명용 영어 (leverage, seamless, robust 등) | 한국어로 풀거나, 첫 등장 한 번만 병기한다 |

### 구조

- lead의 대칭 대구(`A가 아니라 B이며, C가 아니라 D다`)는 한쪽으로 풀어 쓴다.
- `먼저`·`반면`·`결국`이 문단마다 반복되면 줄인다.
- `첫째`·`둘째`·`셋째`는 번호 단계나 `우선` / `그다음`으로 바꾼다.
- 참조·금지·경로 목록의 표와 불릿은 유지한다. 같은 어미·같은 길이로만 늘어선 설명 bullet은 문장이나 표로 나눈다.
- 본편에 이모지와 헤딩 아래 한 줄 요약 박스를 두지 않는다.

### 본편에 새로 넣지 않는 표현

Architecture·프로세스의 lead와 본문에 아래를 새로 쓰지 않는다. 사실·경계·금지만 적는다.

- 의의·중요성 과장 (`괄목할 만한`, `~로 평가된다`)
- `~은 명확하다` / `~은 분명하다`의 반복
- `단순한 X를 넘어 Y`
- `지평을 열다`, `발판을 마련하다`, `토대를 마련하다`

### 이 Kit에 두지 않음

헤딩 삭제, 불릿의 전면 산문화, 쉼표·연결어미 통계의 일괄 적용, im-not-ai 분류 체계·검증 스크립트의 Kit 검사 연동, 대명사 자동 치환은 하지 않는다.

## Kit 문서를 고칠 때

1. 유형을 정한다.
2. lead를 쓴다.
3. 골격을 채운다.
4. rules 요약이 있으면 한 단락만 동기화한다.
5. 손댄 문단·bullet이 **한다체**인지 확인한다 (톤 예외 경로 제외).
6. AI 초안이면 lead 대구·종결 접속사·위 번역투 표를 훑는다.
7. 손댄 구간이 페이지의 약 30%를 넘으면 골격·정본부터 다시 본다.

루트 README · Overview · templates를 **진입**으로 먼저 맞추고, 참조 문서는 lead만 보강해도 된다. lead·수정 구간은 항상 한다체다.
